# Codebase map

[allocationRunService.ts](../src/services/allocationRunService.ts) owns run lifecycle orchestration. `createRunAndQueue` creates a tenant-scoped PENDING row and queues work. `processQueuedAllocationRun` transitions to RUNNING, computes allocation results, replaces rows, then transitions to COMPLETED; the catch directly writes FAILED. `assertValidRunTransition` is defined in the same service and rejects unlisted edges with ValidationError. [allocationRunRepository.ts](../src/repositories/allocationRunRepository.ts) scopes reads and writes by tenant and uses a transaction for result replacement.

The inspected worker uses a read then update transition; it has no conditional count-one claim in this path. The [runtime test](../tests/runtime-allocation-state-lab.test.mjs) imports the actual guard through the VM loader and loads the real error classes while adapting unused repository/engine exports and queue registration. A reviewer should separate state policy, tenant query scope, claim atomicity, result replacement, and audit behavior. Adding a new status requires changes to the type, transition table, repository, UI, and tests. The current course keeps those responsibilities visible without pretending to have a live database. The route layer also authenticates the actor, while this service layer remains responsible for lifecycle ordering and repository coordination.

The queue is an in-process setTimeout callback, not durable storage. A process restart can lose queued execution even though the run record exists. Registration and scheduling are not exercised here.

# Testing and debugging

If a legal edge fails, inspect the `VALID_RUN_TRANSITIONS` table and enum values first. If a terminal row reopens, check that COMPLETED and FAILED arrays remain empty. If an error lacks the requested and current statuses, inspect ValidationError construction. The pure guard should not query repositories or write audits; those belong to service callers.

Run `node --experimental-vm-modules --test tests/runtime-allocation-state-lab.test.mjs` and read [the log](evidence/crud-b07-astra-runtime2.log). The lab executes actual TypeScript with the actual ValidationError and no copied policy algorithm. It cannot prove the worker's claim update, tenant predicate, Prisma SQL, aggregation computation, allocation result replacement, or failure persistence. A follow-up test should force claim count zero and assert no computation. Another should force computation failure and inspect the direct FAILED update; this worker does not emit an audit in the shown processing function. Debug those tests with call order: read, RUNNING update, compute, replace, completion read and update. Do not broaden the pure lab's claims to cover those I/O paths. Keep each follow-up failure test focused on one boundary so a regression has an identifiable owner.

# Concepts: run lifecycle and tenant boundaries

Allocation runs are durable workflow records. PENDING means work can be claimed, RUNNING means a worker owns processing, COMPLETED means allocation result rows and summary were written, and FAILED means terminal failure was recorded. The state guard refuses skipped phases and terminal reopening when a caller invokes it. The worker catch bypasses it to write FAILED. It is a policy function; it cannot make an update atomic.

The repository's tenantId filters are part of identity. A run id alone is insufficient when APIs serve multiple tenants. A stronger worker design would claim only PENDING rows conditionally and check an update count. That safeguard is not implemented by this policy lab. Result replacement uses a transaction for delete/create consistency, while the state guard validates the surrounding transitions. Read [the service](../src/services/allocationRunService.ts) and [repository](../src/repositories/allocationRunRepository.ts) together. The lab proves legal and illegal transition behavior only. It does not prove tenant isolation, claim races, rollback, or retry semantics. If a product needs retries, add an explicit command and transition rather than allowing FAILED to RUNNING silently.
